# FoodGuard 前端深度说明

## 1. 前端定位

FoodGuard 前端负责把复杂的后端分析链路转化为用户可理解的交互流程，重点解决以下问题：

- 降低食品标签分析的使用门槛
- 展示异步分析过程与最终报告
- 把个性化偏好和报告内容结合起来
- 提供围绕单份报告的追问能力

## 2. 应用初始化

入口文件是 `src/main.tsx`，职责很简单：

- 挂载 React 根节点
- 开启 `StrictMode`
- 渲染 `App`

`src/App.tsx` 则负责：

- 初始化 `QueryClientProvider`
- 配置路由
- 安装强制登出处理器
- 按页面做 `React.lazy` 懒加载

本次收尾中，页面已改成路由级懒加载，构建时可以把登录页、历史页、报告详情页等拆成独立 chunk。

## 3. 路由与权限控制

前端路由分两组：

- `AuthLayout`：登录与注册
- `AppLayout`：首页、分析中、历史记录、报告详情、个人中心

权限与引导逻辑由 `AppLayout` 决定：

- 未登录用户跳转到 `/login`
- 已登录但未完成初始化偏好的用户跳转到 `/onboarding`
- 已完成初始化的用户进入主站页面

## 4. 状态管理与鉴权

鉴权核心包含三部分：

### 4.1 Axios 客户端

`src/api/client.ts` 负责：

- 自动附带 access token
- 统一识别标准 API 响应包
- 401 时尝试调用 `/auth/refresh`
- 刷新失败时触发强制登出

### 4.2 本地会话持久化

`src/store/auth.ts` 使用 Zustand 管理：

- 用户信息
- 用户偏好
- 是否已登录
- 是否需要 onboarding

### 4.3 手动退出登录

本次收尾新增了显式的手动退出逻辑：

- 主动点击退出时，会用 `fetch` 调用后端 `/auth/logout`
- 请求体携带当前 `refresh_token`
- 不论网络成功或失败，前端都会清空本地 token 与用户状态并跳转登录页

这样既补齐了服务端撤销 refresh token 的安全闭环，又保证用户不会因为网络问题卡在退出流程中。

## 5. 主要页面流

### 5.1 首页上传

首页负责：

- 选择或拖拽上传图片
- 展示图片预览
- 读取用户默认偏好
- 提交到 `/analysis/upload`

上传成功后会跳转到分析中页面，并把图片预览临时写入 `sessionStorage`。

### 5.2 分析中页面

分析中页面会轮询 `/analysis/tasks/{taskId}`：

- 任务成功时跳转报告详情
- 任务失败时展示失败信息
- 连续多次轮询失败或超过最长等待时间时停止轮询

### 5.3 历史记录

历史记录页面展示报告列表，并支持搜索与删除。

本次收尾修复了删除后的分页错位问题：

- 删除成功后不再本地手动 `filter`
- 改为重新请求当前页
- 以服务端返回的 `page / total / items` 作为唯一真值

这样当用户删除最后一页的最后一条记录时，页面会正确回退到服务端夹取后的上一页。

### 5.4 报告详情与问答

报告详情页负责：

- 展示原图、健康分数、风险项、营养表、配料解析和建议
- 挂载 `ReportChatPanel`

问答面板支持：

- 读取已有会话
- 生成建议问题
- 用 SSE 流式消费回答
- 在流式中断但服务端已持久化答案时尝试恢复

## 6. 组件与目录划分

前端目录按职责组织：

- `src/pages/`: 页面
- `src/components/layout/`: 页面布局
- `src/components/report/`: 报告详情与问答
- `src/components/profile/`: 个人中心表单
- `src/components/ui/`: 基础 UI 组件
- `src/lib/`: 业务辅助逻辑
- `src/types/`: 类型定义

这种划分适合毕业设计展示时从“页面层”往“业务层”解释。

## 7. 测试与工程收尾

前端当前使用 Vitest + Testing Library，覆盖了以下重点能力：

- 分析中轮询失败与超时场景
- 报告问答 markdown 渲染与恢复逻辑
- 修改密码表单的 autocomplete 约束
- 手动退出登录的服务端撤销行为
- 历史记录删除后的分页回源刷新

## 8. 答辩时可重点说明的点

- 为什么分析结果页和问答页适合拆成懒加载：首屏更快、报告详情依赖较重
- 为什么 token 刷新放在 Axios 拦截器里：统一处理 401，减少页面散落逻辑
- 为什么删除历史记录后重新请求列表而不是本地维护分页：以后端分页结果为准，更稳、更简单
- 为什么问答流要有恢复机制：大模型流式返回容易中断，但持久化结果不应丢失
